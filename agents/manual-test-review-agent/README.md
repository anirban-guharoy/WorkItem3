# Manual Test Review Agent

An independent LangChain service that evaluates the test case set produced by Manual Test Agent.
It checks acceptance-criterion coverage, executability, verifiable outcomes, duplicates, reasonable
priorities/types, and unsupported assumptions. Cases are automatically created as Xray Cloud Manual
tests only when the reviewer returns `approved`. The reviewer treats the submitted, pre-generated
test cases as its review input (not a request to generate replacements), follows the shared
`@workitem3/test-case-contract` format, and considers relevant risk-based and structured test-design
techniques when assessing coverage.

## Run locally

From the repository root:

```bash
npm install
cp agents/manual-test-review-agent/.env.example agents/manual-test-review-agent/.env
npm run start --workspace=@workitem3/manual-test-review-agent
```

The service listens on port `3001` by default. Configure `MCP_SERVER_URL` (and optional
`MCP_SERVER_TOKEN`) for `common-mcp-server`; the service requires MCP tools to be available and
uses its retrieved evidence when reviewing. Configure the Azure AI Foundry endpoint and API key
through the environment and deploy the model selected in `config/models.json`.

The reviewer defaults to the distinct `claude-opus-4-1` Foundry model deployment, while the generator
defaults to `claude-sonnet-4-5`. Ensure the reviewer model is deployed and available in your Foundry
resource; change its own `config/models.json` or mounted AKS ConfigMap if needed. The two agents do
not share model selection.

Configure an Xray Cloud API key with `XRAY_CLIENT_ID` and `XRAY_CLIENT_SECRET`. Set
`XRAY_BASE_URL` to your Xray Cloud region (`https://xray.cloud.getxray.app` by default; regional
hosts are supported) and optionally choose `XRAY_TEST_CYCLE_NAME`. Approved cases are created in the
JIRA project encoded in the story key, then added to an existing test execution with that name or a
new execution is created. A review that requests changes does not create anything in Xray.

## API

`POST /review` accepts the story and the complete `testCaseSet` generated by Manual Test Agent. Both
are validated against the shared `@workitem3/test-case-contract` schema.

```json
{
  "story": {
    "key": "DEMO-1",
    "summary": "User login",
    "description": "Users can sign in with their account.",
    "acceptanceCriteria": "- Valid credentials sign in\n- Invalid credentials show an error"
  },
  "testCaseSet": {
    "summary": "Login behavior",
    "assumptions": [],
    "contextSources": [],
    "testCases": [
      {
        "id": "TC-001",
        "title": "Sign in with valid credentials",
        "type": "functional",
        "priority": "High",
        "acceptanceCriterion": "Valid credentials sign in",
        "preconditions": ["An active user account exists"],
        "steps": ["Open the login page", "Enter valid credentials", "Submit the form"],
        "expectedResult": "The user is signed in and the authenticated page is shown"
      }
    ]
  }
}
```

The response's `review` object contains `reviewStatus` (`approved` or `changes_requested`),
criterion-level coverage, actionable findings, and the titles/URLs of external documents actually
used in `contextSources`. Publication also requires every reported criterion to be `covered` and no
critical/major findings. When approved and Xray publishing succeeds, `status` is `published` and
`xray` contains the test keys and test execution. A non-approved review returns
`status: "changes_requested"` with no Xray writes. Invalid input returns HTTP 400; MCP/model failures
return HTTP 502, missing Xray credentials return HTTP 503, and Xray publish failures return HTTP 502
with saved progress. Repeating the same request returns its saved result; incomplete publication
resumes from persisted progress. A concurrent request for the same set returns HTTP 409.
`GET /healthz` provides a Kubernetes health check.

## Docker and Azure AKS

Build/push the reviewer independently from the repository root:

```bash
docker build -f agents/manual-test-review-agent/Dockerfile \
  -t <ACR_NAME>.azurecr.io/manual-test-review-agent:1.0.0 .
az acr login -n <ACR_NAME>
docker push <ACR_NAME>.azurecr.io/manual-test-review-agent:1.0.0
kubectl apply -f agents/manual-test-review-agent/k8s/deployment.yaml
kubectl -n manual-test-reviewer create secret generic manual-test-reviewer-secrets \
  --from-env-file=agents/manual-test-review-agent/.env
```

The reviewer runs in its own namespace with a ClusterIP Service and no public ingress by default. In
cluster, call `http://manual-test-reviewer.manual-test-reviewer.svc.cluster.local/review`; for local
testing use `kubectl -n manual-test-reviewer port-forward svc/manual-test-reviewer 3001:80`. The
reviewer secret must include the MCP URL/token, Foundry endpoint/key, and Xray credentials. It runs
as one replica with an Azure Disk PVC to persist review decisions and resumable Xray publication;
keep this storage when replacing the pod. Configure an ingress or gateway separately if external
access is required.

## Entra ID and LangSmith

`GET /api/status` requires a v2 Entra access token for this API registration with delegated
`Agent.Read` and the `DevOps` app role; `POST /review` requires `Agent.Invoke`. Configure
`ENTRA_TENANT_ID`, `ENTRA_API_AUDIENCE`, `ENTRA_READ_SCOPE`, `ENTRA_INVOKE_SCOPE`,
`ENTRA_DEVOPS_ROLE`, and the exact `DASHBOARD_ORIGIN`. `/healthz` remains open for Kubernetes
probes. Configure the app-role assignment on this API registration as described in
[LangSmith UI setup](../../apps/langsmith-ui/README.md).

Set `LANGSMITH_TRACING=true`, `LANGSMITH_API_KEY`, `LANGSMITH_ENDPOINT`, and `LANGSMITH_PROJECT` to
trace reviewer runs. See [LangSmith UI setup](../../apps/langsmith-ui/README.md) for registration
and tenant consent instructions.
